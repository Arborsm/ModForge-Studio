# ModForge Studio 项目计划

## 1. 项目定位

`ModForge Studio` 的目标是为《星露谷物语》模组作者提供一个桌面端、可视化、以编辑器工作流为中心的内容创作工具。它不是简单的网页面板，而是希望逐步接近 IDE / 地图编辑器 / 剧情工具的综合体验。

当前阶段已经证明下面这条技术路线可行：

- 前端交互和编辑器 UI：`React + TypeScript`
- 桌面宿主与本地能力：`Tauri 2`
- 未来游戏兼容桥接：`.NET 8 sidecar`

## 2. 当前项目边界

### 已经落地的范围

- 游戏目录探测与校验
- `TMX` 地图扫描与解析
- 世界地图 `World Atlas` 聚合视图
- 地图标签页、图层控制、对象组检查与视口交互
- 事件文件扫描、解析、时间线与舞台回放
- 玩家外观配置窗口与事件舞台中的 farmer 预览
- IDE 风格工作区系统：停靠、浮窗、布局持久化、预设

### 尚未落地的范围

- `XNB` 加载与回写
- `.NET bridge` 真正承载游戏兼容逻辑
- 地图对象编辑闭环
- 角色 / 建筑 / 物品编辑器
- 完整 CP 导入、反向工程与导出

## 3. 核心产品目标

长期目标：

- 导入游戏原始资源与现有模组资源
- 用可视化方式编辑地图、事件、角色、建筑、物品与本地化内容
- 提供校验、诊断和最终导出
- 为后续插件化留出明确边界

短中期目标：

- 先把“读得进、看得见、查得准、能定位”做实
- 再逐步推进“能编辑、能回写、能导出”

## 4. 现阶段技术结论

### 4.1 桌面形态是必须的

该项目不适合只做浏览器版，原因很直接：

- 需要稳定访问本地游戏目录与大量资源文件
- 需要后续对接游戏程序集和本地 sidecar
- 需要桌面应用级别的窗口、布局和资源权限控制

因此当前选择 `Tauri + React` 是合理的。

### 4.2 地图加载应坚持统一内部模型

无论资源来自：

- `TMX`
- `XNB`
- Content Patcher patch
- 未来的插件导入器

最终都应统一归一到内部模型，而不是把前端直接绑死在原始文件格式上。当前的 `MapDocument` 路线是对的，后续应继续维持。

### 4.3 `.NET bridge` 暂时可以延后，但不能取消

当前项目的实用功能主要靠 `Tauri + Rust + 前端解析` 已经能跑起来，这很好。但一旦进入下面这些需求，就需要把 `.NET bridge` 真正做起来：

- `XNB` 解析
- 更贴近原版的地图/事件兼容逻辑
- 需要复用游戏程序集的数据结构或推导行为

## 5. 当前功能分层

### Presentation Layer

负责：

- 顶栏与模块切换
- 工作区布局系统
- 地图视口
- 事件舞台
- 面板、检查器、状态栏

对应主要文件：

- `apps/desktop/src/App.tsx`
- `apps/desktop/src/components/*`

### Application Layer

负责：

- 管理地图工作区状态
- 管理事件工作区状态
- 管理窗口、布局和用户配置

对应主要文件：

- `apps/desktop/src/lib/app/useMapWorkspace.ts`
- `apps/desktop/src/lib/app/useEventWorkspace.ts`
- `apps/desktop/src/lib/app/workspacePanels.tsx`

### Domain Layer

负责：

- 地图数据结构
- 事件数据结构
- 玩家外观数据结构

对应主要文件：

- `apps/desktop/src/lib/maps/types.ts`
- `apps/desktop/src/lib/events/types.ts`
- `apps/desktop/src/lib/app/types.ts`

### Infrastructure Layer

负责：

- 文件系统与 Tauri 命令
- 地图扫描、事件扫描、文本与图片读取
- 未来 sidecar 通信

对应主要文件：

- `apps/desktop/src/lib/desktop.ts`
- `apps/desktop/src-tauri/src/lib.rs`
- `services/sdv-bridge/*`

## 6. 路线图

### 阶段 A：地图与事件阅读器

目标：完成资源读取、解析、可视化查看与导航。

当前状态：大部分已经完成。

已完成：

- 地图扫描与 `TMX` 解析
- `World Atlas`
- 地图标签页
- 图层和对象组检查
- 事件扫描、事件解析、时间线、舞台回放
- 玩家外观配置窗口
- 工作区停靠系统

### 阶段 B：地图编辑 MVP

目标：从只读检查升级到可编辑。

优先内容：

- 对象点击选择
- 对象高亮状态
- 基础属性检查器
- 位置与尺寸修改
- 属性写回到内部状态

暂不要求：

- 复杂画刷系统
- 完整撤销重做
- 真正导出 TMX / CP

### 阶段 C：事件与角色演出增强

目标：提高事件工作区的可用度和真实性。

优先内容：

- 补齐事件命令覆盖率
- 强化事件图结构与命令关系可视化
- 提升 farmer 渲染与原版一致性
- 让事件舞台支持更多状态来源

### 阶段 D：`XNB` 与 sidecar

目标：打通原版资产兼容路径。

优先内容：

- `.NET bridge` 从占位变成可调用服务
- 设计 `XNB -> MapDocument` 的转换协议
- 统一前端 DTO，避免直接暴露 .NET 类型

### 阶段 E：模组工作流

目标：真正进入“导入已有模组 -> 编辑 -> 校验 -> 导出”。

优先内容：

- `manifest.json`
- `content.json`
- Content Patcher 目标资源解析
- 诊断与导出

## 7. 当前优先级建议

推荐优先级：

1. 地图对象选择与编辑
2. 对象检查器与属性写回
3. 事件工作区命令覆盖率
4. 农夫渲染精度继续提升
5. `XNB` 兼容与 `.NET bridge`
6. 角色 / 建筑 / 物品模块从蓝图转真实编辑器

## 8. 已知技术风险

### 8.1 资源格式差异

风险：

- 有的用户只有 `XNB`
- 有的用户依赖 `Content (unpacked)`
- 不同资源工具可能生成不同细节

应对：

- 坚持统一内部模型
- 当前优先做 `TMX`
- 后续再补 `XNB`

### 8.2 原版逻辑复现复杂

风险：

- 事件命令和 farmer 渲染都包含大量隐含状态
- 仅靠截图或表面效果修补会越来越脆

应对：

- 优先追原版代码路径
- 用反编译与真实事件数据交叉校验
- 把“状态准备”和“渲染”职责分开

### 8.3 工作区复杂度继续增长

风险：

- 面板、浮窗、停靠和预设已经较复杂
- 如果后续模块继续增多，容易出现状态耦合

应对：

- 继续让 `workspacePanels.tsx` 作为装配层
- 避免把业务逻辑塞进布局组件
- 按模块收束状态，不让 `App.tsx` 无限膨胀

## 9. 近期执行建议

如果只做下一轮高价值推进，建议按这个顺序：

1. 先把地图对象点击选择和右侧检查器打通。
2. 给对象编辑增加内部状态修改，但先不急着落盘。
3. 补事件舞台最常见缺失命令。
4. 继续沿原版代码补 farmer 渲染分支。
5. 再启动 `.NET bridge` 的真实协议设计。

## 10. 结论

当前项目已经越过“空壳搭架子”的阶段，进入“真实工具原型”阶段。接下来最重要的不是继续堆更多占位模块，而是把现有地图与事件能力从“能展示”推进到“能编辑、能验证、能复用”。

这意味着近期的正确策略应当是：

- 减少纯展示型扩张
- 优先补齐地图对象编辑闭环
- 继续稳步提高事件与 farmer 渲染的真实性
- 等前端内部模型稳定后，再接 `.NET bridge` 和 `XNB`
